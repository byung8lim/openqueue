# OpenQueue 개발요청서

## Claude 기반 바이브 코딩 프로젝트 실행 지침 및 개발 요구사항

-   문서 버전: 1.0
-   대상 솔루션: OpenQueue (가칭) --- Java 기반 Virtual Waiting Room
-   개발 방식: Claude를 활용한 단계적·점증적 바이브 코딩
-   핵심 원칙: 명세 우선, 모듈화, 한국어 주요 주석, TDD, 보안 우선, 회귀
    검증
-   상위 설계 참조: `openqueue_architecture_security_design_ko.md`

## 1. 프로젝트 목적

OpenQueue는 웹사이트 또는 API에 접속이 집중될 때 사용자를 대기열에
등록하고, 사전에 정의된 정책에 따라 순차적 또는 제한적으로 서비스에
입장시키는 독립형 Virtual Waiting Room 솔루션이다.

Claude를 이용한 바이브 코딩 방식으로 개발하되, 단순히 빠르게 코드를
생성하는 것이 목표가 아니다. **사람이 코드를 읽고, 디버깅하고, 원인을
추적하고, 안전하게 확장할 수 있는 기업용 소프트웨어**를 만드는 것이
목표다.

Claude가 생성한 코드는 모두 사람이 검토하고 테스트할 수 있어야 하며,
구현 근거가 되는 요구사항·설계·테스트가 추적 가능해야 한다.

## 2. 반드시 준수할 개발 원칙

### 2.1 명세 기반 개발

-   모든 기능은 요구사항 명세서의 고유 기능 ID와 연결한다.
-   화면의 작은 동작, API 입력 검증, 오류 처리, 상태 전이 등 세부 기능도
    명세한다.
-   명세가 모호하거나 상충하면 코드를 작성하기 전에 질문하고 결정 사항을
    기록한다.
-   명세에 없는 동작을 Claude가 임의로 추가하지 않는다.
-   요구사항 → 설계 → 코드 → 테스트 → 검증 결과의 추적성을 유지한다.

### 2.2 모듈화와 가독성

-   기능별 책임을 분리하고 단일 책임 원칙을 적용한다.
-   한 클래스나 함수가 여러 업무 책임을 떠안지 않도록 한다.
-   사람이 쉽게 읽고 디버깅할 수 있는 명확한 이름과 단순한 제어 흐름을
    사용한다.
-   과도한 추상화, 불필요한 디자인 패턴, 지나치게 짧은 코드, 한 파일에
    몰아넣는 구현을 금지한다.
-   Controller에 업무 규칙을 넣지 않고 Domain/Application 계층에 둔다.
-   DB·Redis·외부 시스템 연계는 Adapter/Repository로 분리한다.
-   순환 의존성을 금지하고 모듈 간 계약을 명시한다.

### 2.3 한국어 주석 및 문서화

-   주요 업무 로직, 보안 검증, 동시성 제어, 상태 전이, 예외 처리 및
    복잡한 알고리즘의 주석은 한국어로 작성한다.
-   클래스와 공개 메서드에는 목적, 입력, 출력, 예외 및 주의사항을
    문서화한다.
-   주석은 코드 내용을 반복하지 말고, 왜 필요한지와 어떤 불변조건을
    보호하는지를 설명한다.
-   식별자, API 필드, 표준 기술 용어는 일관성을 위해 영어 사용을
    허용한다.
-   주석과 코드의 동작이 달라지면 반드시 함께 수정한다.
-   파일 인코딩은 UTF-8로 통일한다.

### 2.4 TDD 필수 적용

모든 기능은 다음 순서로 개발한다.

1.  요구사항과 수용 기준 확정
2.  테스트 케이스 작성
3.  테스트 실행 및 실패 확인(Red)
4.  최소 구현
5.  테스트 통과(Green)
6.  리팩터링
7.  관련 테스트 전체 재실행
8.  정적 분석 및 보안 검사
9.  코드 리뷰
10. 요구사항 추적표 갱신

테스트를 통과시키기 위해 테스트를 삭제·비활성화하거나 검증을 약화하지
않는다. 테스트가 없는 기능은 완료 처리하지 않는다.

### 2.5 점증적 개발 및 변경 영향 검증

-   작은 기능 단위로 구현하고 각 단위마다 테스트와 코드 리뷰를
    통과시킨다.
-   전체 시스템을 한 번의 프롬프트로 대량 생성하지 않는다.
-   앞 단계의 변경이 이전·현재·다음 단계에 미치는 영향을 분석한다.
-   변경된 모듈뿐 아니라 의존 모듈의 회귀 테스트를 수행한다.
-   DB/API/Redis/정책/토큰 계약 또는 보안 경계 변경은 별도 승인과 강화된
    검증을 요구한다.

### 2.6 기업 환경 보안

-   DMZ, 내부 관리망, DB Zone, 내부 서비스망의 네트워크 분리를 준수한다.
-   기본 거부(Default Deny), 최소 권한, Zero Trust를 적용한다.
-   DMZ 구성요소에서 내부 MariaDB 및 관리자 시스템으로 직접 접근할 수
    없도록 한다.
-   대기열 Redis는 DMZ 전용으로 배치하고 인터넷에 노출하지 않는다.
-   내부 원본 서비스는 인터넷에 직접 노출하지 않는다.
-   동적 라우팅은 등록된 백엔드 allowlist만 사용하며 임의 URL 프록시를
    금지한다.
-   입장 토큰은 내부 API Ingress에서 최종 검증한다.

## 3. Claude 바이브 코딩 운영 규칙

### 3.1 Claude의 역할

Claude는 요구사항 분석, 설계 초안, 테스트 작성, 구현, 리팩터링, 영향도
분석, 테스트 결과 해석 및 문서화를 지원한다.

단, 사람의 승인 없이 다음 사항을 임의로 변경해서는 안 된다.

-   네트워크 보안 경계 및 Zone 간 통신
-   인증·인가 구조
-   암호키 보관 및 토큰 서명 방식
-   DB/Redis/API/정책 스키마 계약
-   모듈 경계와 배포 경계
-   데이터 보존 및 장애 시 Fail-open/Fail-closed 정책

### 3.2 작업 전 절차

각 작업 전에 반드시 다음을 수행한다.

1.  관련 요구사항 ID와 승인된 명세를 확인한다.
2.  저장소 구조와 현재 소스코드를 확인한다.
3.  관련 테스트 및 기존 테스트 결과를 확인한다.
4.  호출·의존 모듈과 데이터 흐름을 분석한다.
5.  변경 대상 파일 및 목적을 제시한다.
6.  이전·현재·다음 단계 영향도를 분석한다.
7.  TDD 테스트 계획을 제시한다.
8.  보안 및 네트워크 영향도를 검토한다.
9.  승인된 범위 내에서만 구현한다.

명세가 불명확하거나 보안상 중요한 결정이 필요하면 임의로 가정하지 말고
질문한다.

### 3.3 작업 후 필수 보고 형식

``` text
[작업 결과]
1. 작업 ID:
2. 관련 요구사항 ID:
3. 구현 내용:
4. 변경 파일:
5. 설계 변경 여부:
6. 영향도 분석:
   - 이전 단계:
   - 현재 단계:
   - 다음 단계:
7. 작성/수정한 테스트:
8. 실행한 테스트 명령:
9. 실제 테스트 결과:
10. 정적 분석 결과:
11. 보안 검토 결과:
12. 미해결 사항:
13. 다음 작업 제안:
```

테스트를 실행하지 못했으면 통과라고 표시하지 말고 미실행 사유와 잔여
위험을 기록한다.

### 3.4 토큰 효율 절차 (2026-11-15 부터 적용, §2.4·§3.2·§3.3 에 우선)

소유자 결정: 진행 속도 대비 토큰 소모가 과다하여 아래 절차로 전환한다. 목표는 **토큰당 개발 속도 최대화**이며, 검증 게이트 자체는 유지한다.

**단위 작업(Unit)** — Phase 를 파일 몇 개 규모의 작은 단위로 쪼갠다. 각 단위 작업은 다음만 수행한다.

1. 테스트 코드와 구현을 **함께** 작성한다(TDD 기반 검증 설계는 유지, Red 실행 생략).
2. `mvn`·`npm test` 등 테스트 **실행은 하지 않는다**. 컴파일 확인도 생략한다(IDE 진단이 무료로 보이면 활용 가능).
3. 끝나는 즉시 `docs/CHECKPOINT.md` 의 해당 행을 `done` 으로 바꾸고 "다음 할 일"·"미결" 을 갱신한다. 이 갱신이 단위 작업의 종료 조건이다.
4. 사용자에게는 1~2줄로만 알린다. 계획 설명·보고서·추적표 갱신은 하지 않는다.

**Phase 게이트** — Phase 의 모든 단위 작업이 `done` 이 되면 한 번만 수행한다.

1. `cd backend && mvn verify` 1회 실행(실패 시 수정 후 재실행, 이 반복만 허용).
2. 프런트엔드가 있으면 `npm test`(Vitest) 1회. Playwright/Docker 통합은 CI 에 위임.
3. §3.3 형식 보고서 **1건**, 추적표·PROGRESS·SRS 상태 갱신, 커밋 1~2건.
4. 결정 사항은 D-xxx 로 문서에 기록하고 사후 승인을 묶어서 요청한다(보안 경계 변경만 한 줄로 즉시 짚는다).

**체크포인트 파일(`docs/CHECKPOINT.md`)** — 중단·재개의 유일한 기준.

- 내용: 현재 Phase, 단위 작업 표(ID · 내용 · 상태 `todo|doing|done` · 산출 파일), 다음 할 일 1줄, 미결 목록. 50줄 이내로 유지한다.
- 단위 작업 **시작 시 `doing`**, 종료 시 `done` 으로 바꾼다. 세션이 중간에 끊기면 `doing` 행이 재개 지점이다.
- 재개 절차: `docs/CHECKPOINT.md` 만 읽고 `doing`/첫 `todo` 행부터 이어서 한다. PROGRESS·보고서·설계서는 필요할 때만 해당 구간을 읽는다.
- Phase 게이트 통과 후 표를 비우고 다음 Phase 의 단위 작업 목록으로 교체한다.

**토큰 절약 규칙** — 파일은 필요한 구간만 읽는다. 명령 출력은 `-q`·`grep`·`tail` 로 줄인다. 같은 내용을 여러 문서에 중복 기록하지 않는다. 실행하지 않은 테스트는 여전히 통과로 보고하지 않는다.


## 4. 시스템 아키텍처 및 네트워크 보안 기준

### 4.1 네트워크 Zone

  -----------------------------------------------------------------------
  Zone                    구성요소                접근 원칙
  ----------------------- ----------------------- -----------------------
  Internet                사용자 브라우저         DMZ 공개 진입점만 접근

  DMZ                     외부 LB/WAF, Edge       외부 요청 처리, 내부 DB
                          Gateway, Queue Engine,  직접 접근 금지
                          Waiting Room, Queue     
                          Redis                   

  내부 관리망             Admin Dashboard,        승인된 관리자와 운영
                          Control API, 정책       시스템만 접근
                          검증·서명·배포, IAM,    
                          운영 관리               

  DB Zone                 MariaDB, 내부 감사      승인된 내부 서비스
                          데이터 및 백업          계정만 접근

  내부 서비스망           Internal API Ingress,   인터넷 직접 접근 금지,
                          Business API, Origin    승인된 Ingress 경유
  -----------------------------------------------------------------------

### 4.2 절대 준수 조건

-   DMZ에서 MariaDB 접속을 허용하지 않는다.
-   DMZ에 내부 DB 계정, 관리자 자격증명, 업무 DB 비밀번호를 저장하지
    않는다.
-   Queue Redis는 DMZ 전용 서브넷에 배치하고 인터넷에서 직접 접근할 수
    없게 한다.
-   Redis는 Queue Engine에 필요한 최소 권한만 부여한다.
-   DMZ Gateway는 등록된 내부 API Ingress 목적지로만 통신한다.
-   임의 URL을 전달받아 프록시하는 기능을 구현하지 않는다.
-   내부 원본 서버는 인터넷에서 직접 접근할 수 없도록 한다.
-   내부 API Ingress에서 입장 토큰과 요청 권한을 다시 검증한다.
-   정책은 내부 Control Plane에서 생성·검증·서명하고 DMZ에서 검증 후
    적용한다.
-   DMZ 침해를 가정하고 내부 확산을 방지한다.
-   Zone 간 통신은 기본 차단하고 승인된 출발지·목적지·포트·프로토콜만
    허용한다.
-   허용 통신에는 TLS, 서비스 간 mTLS 및 최소 권한을 적용한다.

### 4.3 Control Plane / Data Plane

**Control Plane --- 내부 관리망** - Admin Dashboard - Control API -
Site/Service Registry - Queue Policy 및 Routing Policy 관리 - 정책
버전·승인·서명·배포 - IAM 및 감사 - MariaDB 연계

**Data Plane --- DMZ** - Edge Gateway - Queue Engine - Waiting Room -
Queue Redis Adapter - Dynamic Routing Runtime - Token Service Adapter

Data Plane은 내부 MariaDB를 조회하지 않는다. 내부 정책 DB의 데이터가
필요하면 서명된 정책 스냅샷을 배포받아 검증 후 메모리에 적용한다.

### 4.4 정책 배포 및 토큰 신뢰

-   정책은 immutable version snapshot으로 생성하고 서명한다.
-   DMZ 노드는 서명, 발행자, 버전, 스키마, 유효기간 및 목적지
    allowlist를 검증한다.
-   검증 성공 시 런타임 설정을 원자적으로 교체한다.
-   실패 시 마지막 정상 정책을 유지한다.
-   노드별 적용 버전과 실패 상태를 관리한다.
-   토큰 서명은 HMAC보다 비대칭 서명(예: Ed25519)을 우선 검토한다.
-   개인키는 내부 KMS/HSM 또는 보호된 서명 서비스에 두는 것을 기본
    방향으로 한다.
-   DMZ에는 검증용 공개키만 배포하는 방안을 우선한다.
-   DMZ가 서명 요청을 해야 한다면 mTLS, claim 제한, 짧은 만료, 발급량
    제한 및 감사 기록을 강제한다.
-   내부 Ingress는 서명, `iss`, `aud`, `exp`, `nbf`, `jti`, `site_id`,
    `queue_id`, `scope`를 검증한다.
-   토큰 원문과 비밀정보를 로그에 기록하지 않는다.

### 4.5 동적 라우팅 및 SSRF 방어

-   운영 라우트는 내부 Control Plane에서 관리한다.
-   Gateway 재기동 없이 런타임 정책을 갱신한다.
-   백엔드 서비스 ID를 참조하고 임의 URL을 직접 입력하는 자유 프록시를
    금지한다.
-   목적지 host/port/protocol allowlist를 적용한다.
-   DNS 해석 결과와 최종 연결 목적지를 검증한다.
-   loopback, link-local, metadata endpoint 및 미승인 대역을 차단한다.
-   DNS rebinding, redirect 및 Host 헤더 변조를 고려한다.
-   네트워크 egress 방화벽에서도 허용 목적지 외 연결을 차단한다.

### SQL 분리 원칙

-   SQL을 Java 문자열로 하드코딩하지 않는다.
-   DDL/DML 및 migration SQL은 별도 `.sql` 파일로 관리한다.
-   Flyway migration을 버전 순서로 관리한다.
-   동적 SQL은 파라미터 바인딩을 사용한다.
-   테이블·컬럼·인덱스 변경 시 ERD와 데이터 사전을 함께 수정한다.
-   SQL 변경 시 Repository 및 migration 테스트를 수행한다.

## 8. TDD 및 테스트 전략

### 8.1 테스트 종류

**단위 테스트** - Domain 규칙, FIFO, 입장 인원 계산, TTL/lease 상태
전이 - 정책 검증, 토큰 claim 검증, 입력값 검증, 오류 매핑, 권한 판단

**통합 테스트** - MariaDB Repository, Redis Adapter 및 Lua 원자 연산 -

**계약 테스트** - Control API 요청/응답 - Gateway와 Queue Engine
인터페이스 - 정책 스냅샷 schema - 토큰 claim 및 Internal API Ingress
검증 계약

**E2E 테스트** - 접속 → 대기 등록 → 순번 조회 → 입장 → 원본 서비스
접근 - 대기열 비활성화, 새로고침/재접속, 대기 만료/취소 - 관리자 정책
생성 및 배포

위조·만료·재사용 - 권한 상승·IDOR, Redis ACL - 관리자 API 접근 통제,
로그 민감정보 노출 - TLS/mTLS 인증 실패, rate limit 우회

**성능·복구 테스트** - 동시 접속 급증, 대기열 처리량, SSE 연결 수 -
Redis failover, Gateway/Queue Engine 노드 장애 - 정책 배포 중 재시작,
백업 복구 및 RPO/RTO

## 11. API·DB·Redis·정책 계약 관리

### API

-   경로, method, request/response schema, 오류 코드, 권한을 문서화한다.
-   API 버전 정책을 정의한다.
-   정상 및 주요 오류 응답을 명세한다.
-   공개 API와 내부 관리 API의 네트워크·인증 정책을 분리한다.
-   API 변경은 계약 테스트와 호환성 검증을 수행한다.

### DB

-   테이블·컬럼·인덱스·제약조건을 ERD와 데이터 사전으로 관리한다.
-   migration은 추가 방식 우선으로 작성한다.
-   데이터 손실 가능 변경은 별도 승인과 복구 계획을 요구한다.
-   migration 실패 복구 절차를 문서화한다.
-   Java 코드에 SQL 문자열을 하드코딩하지 않는다.

### Redis

-   key prefix, 자료구조, 값 schema, TTL을 문서화한다.
-   key에 site/queue 범위를 포함한다.
-   key 변경 시 기존 데이터 호환·전환·정리 계획을 수립한다.
-   Lua Script의 입력·출력·원자성·오류 코드를 문서화한다.
-   Redis를 영속 정책 DB로 사용하지 않는다.

### 정책 스키마

-   schema version과 canonical payload 규칙을 정의한다.
-   발행자, 발행 시각, 버전, 유효기간, 대상 환경을 포함한다.
-   알 수 없는 필드와 미지원 버전 처리 방식을 정의한다.
-   검증 실패 시 마지막 정상 설정을 유지한다.
-   롤백은 감사 가능한 새 배포 버전으로 처리한다.

## 12. 보안 개발 규칙

-   소스코드·Git·테스트 코드에 비밀정보를 기록하지 않는다.
-   `.env` 및 Secret 파일을 저장소에서 제외한다.
-   운영 비밀정보는 Vault/KMS/기업 표준 Secret Manager로 관리한다.
-   로그·예외·HTTP 응답에 비밀정보를 노출하지 않는다.
-   관리자 UI/API에 인증과 RBAC를 적용한다.
-   서비스 간 통신은 mTLS 또는 승인된 동등 수준의 상호 인증을 사용한다.
-   모든 외부 입력을 신뢰하지 않는다.
-   URL, Host, path, header, redirect 목적지를 검증한다.
-   SSRF, DNS rebinding, path traversal, header injection을 방어한다.
-   토큰은 짧은 만료시간과 재사용 방지 정책을 적용한다.
-   관리자 로그인, 정책 변경, 권한 변경, 배포, 롤백을 감사 기록한다.
-   DMZ가 내부 감사 기록을 삭제·수정할 수 없게 한다.

## 13. Definition of Done

기능 하나를 완료로 인정하려면 다음을 모두 충족해야 한다.

1.  승인된 요구사항 ID와 수용 기준이 존재한다.
2.  설계 문서와 인터페이스가 갱신되어 있다.
3.  테스트 우선 개발 절차를 따랐다.
4.  정상·경계·오류 테스트가 작성되어 있다.
5.  단위 테스트가 통과했다.
6.  필요한 통합·계약·E2E 테스트가 통과했다.
7.  변경 영향도 분석과 회귀 테스트가 통과했다.
8.  정적 분석과 보안 검사를 통과했다.
9.  한국어 주요 주석과 문서화가 반영되어 있다.
10. 운영 로그와 오류 처리가 적절하다.
11. 비밀정보가 노출되지 않는다.
12. 운영·설치 문서가 갱신되어 있다.
13. 테스트 명령과 실제 결과가 기록되어 있다.
14. 미해결 위험과 제한사항이 명시되어 있다.

테스트가 통과하지 않았거나 수행되지 않은 기능은 완료로 표시하지 않는다.

## 14. Git 및 코드 변경 관리

### 브랜치

-   `main`: 검증된 통합 브랜치
-   `feature/<요구사항ID>-<기능명>`: 기능 개발
-   `fix/<요구사항ID>-<결함명>`: 결함 수정
-   `release/<버전>`: 릴리스 안정화가 필요한 경우

``` text
feat(QUE-001): FIFO 대기열 등록 기능 구현
```

않는다. 비밀정보와 로컬 환경 설정을 커밋하지 않는다.

### Pull Request 필수 항목

-   영향도 등급과 분석
-   테스트 목록과 실제 결과
-   보안 영향
-   DB/Redis/API/정책 schema 변경 여부
-   문서 변경 여부

## 18. 최종 개발 승인 기준

화면이 동작하거나 API가 응답하는 것만으로 개발 완료를 판단하지 않는다.

-   요구사항 명세와 구현이 일치한다.
-   모든 기능에 테스트 증거가 존재한다.
-   이전 단계 변경에 대한 회귀 검증이 완료되었다.
-   DMZ와 내부망·DB Zone의 보안 경계가 검증되었다.
-   DMZ 침해 가정 하에 내부 자산 접근이 차단된다.
-   정책 서명 및 토큰 검증이 독립적으로 검증된다.
-   동시 입장 상한과 대기열 무결성이 부하 테스트로 검증된다.
-   운영자가 장애 원인과 상태를 확인할 수 있다.
-   설치·업그레이드·롤백·백업·복구 절차가 검증되었다.
-   코드와 문서가 사람이 유지보수할 수 있는 수준으로 정리되었다.
-   보안·성능·라이선스·공급망 검토 결과가 기록되었다.

**최종 원칙:** Claude가 코드를 생성했다는 사실은 구현 완료의 근거가
아니다. 승인된 명세, 사람이 검토 가능한 코드, 자동화된 테스트 결과,
영향도 분석 및 보안 검증이 모두 갖춰져야 해당 기능을 완료로 인정한다.
